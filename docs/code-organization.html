Executive summary

The platform works and is in production. Nothing about its behaviour needed changing — the problem was that everything lived in one flat directory, in a handful of very large files, with no way to tell whether a change had broken anything.

Three things mattered most, and all three are now fixed:

  • The whole repository was being served over HTTP. express.static(__dirname) pointed at the repo root, so /server.js, /db.js, /schema.sql and /seed.sql were all publicly readable — the entire authentication implementation and the seed credentials among them. This was verified live, not inferred.
  • There was no way to verify a refactor. No tests, no scripts, no type checking. Any restructuring would have been done blind against a live production database.
  • Files were organised by accident. app.js had grown to 6,396 lines by appending each new phase to the end, so every feature was scattered across four to six non-adjacent regions of the file.

The work was done on a branch, in four verified commits. Because route order and the auth matrix are load-bearing in this codebase, both were captured as machine-checkable baselines before anything moved, and every commit was checked against them.

The headline result: the backend went from 5 flat files to a layered src/server/ tree, the 825-line route grab-bag became 7 domain modules, and source-code disclosure is closed — with the API contract proven byte-identical at every step: 134 router layers in the same order, 127 routes with the same auth matrix and the same response shapes.

What was actually wrong

Each item here was verified by running something, not by reading code and guessing.

Critical  The entire repository was readable over HTTP

express.static(__dirname) served the repo root as the web root. Backend source, the schema, and the seed file with its credentials were all fetchable.

GET /db.js -> 200 3,308 b full source GET /server.js -> 200 52,210 b entire auth implementation GET /seed.sql -> 200 14,513 b seed data incl. credentials GET /schema.sql -> 200 12,063 b full schema

.env itself was not exposed — dotfiles fall through to the SPA shell — but everything else was.

Structural  Every feature was scattered across the file

app.js grew by appending: each phase (REQ-xx, "Phase 6", "was a toast-only shell") went on the end rather than next to related code. The result is that no feature lives in one place.

Event Planner ~1,604 loc across 5 ranges 1373-2262, 5424-5484, 5701-5797, 5798-5872, 5873-6353 Giving ~400 loc across 6 ranges 2525-2586, 2914-3002, 3640-3668, 5023-5165, 5485-5535 Jobs ~304 loc across 4 ranges 2623-2771, 3003-3080, 5191-5267 Events ~284 loc across 4 ranges 1290-1372, 2587-2622, 4718-4756, 4897-5022

Duplication  The same response wrapper, written four times

ok(res, fn) appeared in three files, four times, byte-identical. Confirmed identical before consolidating — a subtle difference would have made merging them a behaviour change.

routes_v2.js:62 routes_planner.js:17 routes_planner.js:69 routes_compliance.js:18 const ok = (res, fn) => fn().catch(err => res.status(500).json({ error: err.message }));

Dead code  Three functions defined twice, later definition silently winning

showEditProfile, showEditProfileV2 and handleSaveProfileV2 each had two definitions. The earlier ones rendered hardcoded mock data; the later, API-backed ones win at load time. The earlier bodies were unreachable and are removed.

Trap  Four more functions are defined twice — and must stay that way

These look identical to the case above and are not. They are decorator wrappers: the second definition captures the first and delegates back to it.

function filterDirectory(value) { … } // app.js:1004 original const _origFilterDir = filterDirectory; // app.js:2900 captures it filterDirectory = function (value) { // app.js:2902 replaces it …; _origFilterDir(value); // and calls the original };

Three of the four call their captured original. Deleting the first definition — or hoisting the second over it — makes the wrapper capture itself and recurse forever. I made exactly this mistake mid-refactor and caught it before committing; the verification tool now detects the _orig capture and reports these separately from real duplicates, so the distinction is enforced rather than remembered. The same applies to switchAnalytics, filterEvents and switchAdmin.

Bug  The profile page shows hardcoded data to every user

FULL_USER_PROFILE (app.js:4288) is a mock object holding one person's name and student ID. Nothing ever hydrates it from the API, but render10SectionProfile() is live — called from showPage() whenever the profile page opens. Every user sees the same hardcoded identity, and a successful profile save re-renders the mock over the real values.

This is a product bug, not dead code, so it is reported rather than silently changed.

Gap  No repository layer, 176 inline queries

SQL is written directly inside route handlers throughout: 55 db.query calls in server.js, 76 in routes_v2.js, 20 in the planner, 25 in compliance. This was not changed — introducing a repository layer touches every handler and is a much larger, riskier change than reorganizing files. It is recorded as the main remaining debt.

Why moving files was not enough

This is the part worth reading carefully, because the obvious fix does not work.

Moving the backend out of the root looks like it should fix source disclosure. It does not. The web root is still the repository root, so the files simply reappear at new URLs:

after moving files, before the allow-list
GET /db.js                          -> 404  fixed
GET /migrate_v2.js                  -> 404  fixed
GET /src/server/middleware/auth.js  -> 200  new exposed path
GET /db/seed.sql                    -> 200  new exposed path

The actual fix is to decide what is public rather than to move what is private. src/server/middleware/static-assets.js replaces express.static over the whole tree with an explicit allow-list — the app shell, client scripts, and assets/. Everything else falls through to the existing 404 handlers.

after the allow-list
/server.js  /package.json  /src/server/middleware/auth.js
/db/seed.sql  /db/schema.sql  /scripts/migrate-v2.js
/tools/dump-routes.js  /README.md  /package-lock.json     all 404

/  /index.html  /app.js  /api.js  /styles.css
/manifest.json  /assets/daffodil-logo.svg  /api/health     all 200

One caveat, and it needs your decision. This closes the hole for the Node server. On Vercel the CDN serves the repository root itself, before the function is invoked, so /server.js may still be fetchable in production. The fix is to move the web assets into a public/ directory — Vercel then serves only that — or add a .vercelignore. Both change the deployment layout, which you chose to leave untouched in this pass, so it is recorded as SEC-6 rather than applied.

How every change was verified

The repository had no tests. Rather than restructure blind, the first commit built a safety net — and it is the part of this work with the longest useful life.

ToolWhat it provesWhy it matters here
dump-routes.js Express's route table in registration order Order is load-bearing: /api/events/planner/:id must register before /api/events/:id. A diff catches any reordering.

check-inline-handlers.js Every inline on*= name resolves; separates wrappers from duplicates The 121 inline handlers are the app's real public surface. This is what a modularization would break.

A note on the production database. The app is wired to a live Neon database with 194 real users. An early version of the contract tool probed write routes as an authenticated alumnus, which meant three writes actually executed — a read-all on notifications and a DSAR deletion request that the same run then cancelled. No lasting change, and the account was an existing QA seed row, but the tool was rewritten so writes are probed anonymously only. Worth stating plainly rather than leaving in a log.

Security findings

All six predate this work and are recorded in tools/known-issues.json. Only the first was fixed here, because the rest change product behaviour and are yours to decide.

#FindingStatus
Critical Full backend source served over HTTP. Auth implementation, schema and seed credentials publicly readable. Fixed
High SEC-1 · A donor can confirm their own payment. POST /api/donations/:id/confirm authorises on donor_user_id === req.user.uid and defaults success to true. Any authenticated user can mark their own pending donation SUCCESS, mint a receipt, and inflate campaign totals and the leaderboard — with no money moving. Needs a gateway webhook. Your call.
Medium SEC-2 · Ticket signatures fall back to a hardcoded key. createHmac('sha256', ENCRYPTION_KEY || 'dic-ticket') — without the env var, tickets are signed with a constant that is in the source, so they can be forged. Fail closed, once the key is set everywhere.
Medium SEC-3 · Two endpoints answer unauthenticated callers. GET /api/chapters/:id/members and GET /api/events/planner/:id return real rows with no token — alumni names and ids, and an event's budgets, sponsors and volunteers. Every sibling route requires auth. One-line fix, but it changes the contract.
Low SEC-4 · 500s leak internal error text. ok() returns err.message, exposing SQL and constraint names. Now one function, so a one-line fix.
Low SEC-5 · Database TLS verification disabled. rejectUnauthorized: false accepts any certificate. Needs the provider CA trusted first.
Info SEC-6 · Vercel still serves source statically. The allow-list covers the Node server; the CDN serves the repo root before the function runs. Needs public/ or .vercelignore.

Rules to keep

Four things about this codebase are easy to break by accident. They are enforced by tooling where possible.

  • Route order is part of the program. Concrete paths must register before parameterised ones. src/server/modules/index.js mounts domains in a fixed order — run npm run routes and diff before and after any change to mounting.
  • Never reorder top-level code in app.js. Four decorator wrappers depend on load order, and a hoisted declaration over a captured original causes infinite recursion. Any split must be contiguous.
  • No type="module" on the client. 121 inline handlers resolve against window; module scope would break all of them at once, silently.
  • Adding a file to the repo does not make it public. New web assets must be added to the allow-list in src/server/middleware/static-assets.js, which is the point — the default is private.
